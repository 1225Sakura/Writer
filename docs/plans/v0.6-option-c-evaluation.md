## §2 选项 C 重新评估

### 2.1 选项 C 定义

**删 `src/backend/`**（整个 Python FastAPI 系统），所有"后端"功能（数据库、AI 调用、auth、WebSocket、文件系统）迁移到**纯前端**：

- **数据存储**：IndexedDB（Dexie.js 或裸 IDB API）
- **AI 调用**：直接在 renderer 调用外部 API（fetch）
- **auth**：前端 PKI 或纯客户端 API key 管理
- **WebSocket**：SSE 或 polling
- **files**：浏览器 File API + IndexedDB blob

### 2.2 选项 C 动机

理论上的吸引力：

1. **简化部署**：用户只需下载 Electron app（无 Python 子进程）
2. **减少依赖**：无 SQLAlchemy / alembic / cryptography / fastapi
3. **更小 binary**：Electron-only 安装包
4. **避免 Python 兼容性**：Windows SSL DLL 加载问题、conda vs system Python 冲突

### 2.3 选项 C 风险（实际）

每个"前端简化"都伴随新问题：

| 简化 | 新风险 |
|------|--------|
| 删 FastAPI | Electron renderer 必须 handle SSE + multipart streaming |
| 删 SQLAlchemy | IndexedDB 复杂 schema migration（IndexedDB 没有 alembic 等价物） |
| 删 alembic | Schema 变更需要手动写 IndexedDB version bump + migrate callback |
| 删 auth middleware | API key 现在直接暴露在 renderer Network tab（X-API-Key → no longer server-side） |
| 删 WebSocket | SSE 长连接 + reconnect logic + HTTP/2 multiplexing（前端实现更脆弱） |
| 删 Python 后端 | 用户必须信任 renderer 不向后端泄露 secrets（已通过 v0.5 SecretStr 防护，renderer-only 时更难强制） |

## §3 技术影响矩阵

### 3.1 Provider Resolver → 前端实现

| 当前 backend 能力 | 前端等效实现 | 难度 | 状态 |
|------------------|------------|------|------|
| ProviderResolver（缓存 active provider） | React Context + localStorage cache | 低 | 可行 |
| 5-min TTL | React Query staleTime=5min | 低 | 可行 |
| asyncio.Lock | Web Locks API 或 single-tab coordination | 中 | 可行（但 multi-tab 复杂） |
| SecretStr (memory-safe) | Web Crypto API + sealed envelopes | 中 | 可行（Phase 2+） |

### 3.2 39 个 endpoints → 本地方法 / API stub

按 v0.5 plan §8 manifest 分组：

#### 保留为本地方法（数据在 IndexedDB）

- **CRUD 系列** (35 endpoints)：
  - projects, characters, items, locations, factions, world_settings, rules
  - chapters, outlines, drafts, chat_sessions, chat_messages
  - if_lines, projects/{id}/if-lines
  - context_chunks, snapshots
- **本地实现**：直接读写 IndexedDB（无 HTTP）

#### 改为前端 API stub（AI 相关）

- **AI 系列** (20 endpoints)：
  - ai/generate, ai/fill-fields, ai/rewrite-description, ai/review
  - ai/review-consistency, ai/generate-entity, ai/health
- **本地实现**：fetch + SSE 客户端（Anthropic SDK 不能直接在 browser，需要 fetch wrapper）

#### 不需要后端化（纯前端可解决）

- observability/*（metrics/errors/audit/usage 可改写为 localStorage 事件）
- snapshots/*（全部本地化）
- context/*（embedding + retrieval 全部本地）

#### 真实难题：协调 + 持久化一致性

- **IF fork 冲突检测**：v0.5 用 DB partial unique index `WHERE is_active=1` 保证 only-one-active。当前 backend 在 transaction 内做 activate race 检测。**前端 IndexedDB 无 server-side lock** — multi-tab 切换 active provider 会 race。
- **Snapshot 协调**：当前 backend 通过 `fingerprint` (SHA256) 做 content-addressed dedup。前端 IndexedDB 也能做，但 multi-device sync 完全消失。
- **WebSocket 协调**：chat_ws.py 处理多客户端 chat session state。前端实现需 BroadcastChannel API（single-origin only）。

### 3.3 11 个 model（alembic）→ 全部迁 IndexedDB

当前 model：
```
AIProvider, WritingSettings, AIInspectionResult,
Character, CharacterRelationship, CharacterStoryline,
Item, Location, Outline, Chapter, Draft, Project, IFLine,
ChatSession, ChatMessage, Faction, WorldSetting, Rule,
ContextChunk, ContextStats, ContextWeights,
EngagementScore, CoolPoint, Fulfillment,
PacingCurve, Recommendation,
MetricEvent, ErrorEvent, AuditEvent, UsageEvent,
Snapshot, SnapshotTag
```

共 **~32 models**（11 + 子表 + 子关系）。

**IndexedDB 等价**：每个 model = 1 个 IndexedDB object store。
**alembic 等价**：每次 schema 变更需要：
1. `db.version(N + 1).stores({...})` (Dexie)
2. 写 `.upgrade(N, N+1, tx => { ... })` callback（手动 migrate）

**风险**：
- IndexedDB migration 没有 alembic 的 down_revision / branch detection
- 跨 Electron 版本 schema 升级容易踩坑
- Multi-tab 打开同一 DB 时，version bump 会触发 lock contention

### 3.4 WebSocket → SSE / polling

当前 backend `chat_ws.py` 实现 WebSocket chat（含 ticket-based auth + per-session broadcast）。

**前端等价**：
- **SSE**：`EventSource` API 单向（server → client），client → server 需独立 POST。chat 是双向，不适合纯 SSE。
- **polling**：每 1-2s GET 一次新消息。延迟 + 服务器负载都增加。
- **WebSocket 直接在 main 进程**：Electron main process 可 host WebSocket server（Node.js + ws 包），但失去 FastAPI 的成熟 auth/middleware。

**评估**：可接受（用户体验损失 ~200ms latency），但工程复杂度上升。

### 3.5 auth → 前端 PKI

当前 v0.5 P0-Sec1a：
- AES-GCM encrypt API key（key 来自 OS keychain via python-keyring）
- X-API-Key header middleware（verify_api_key）
- /auth/key/init（首次启动生成 key）+ /auth/key/refresh（rotate）

**前端等价**：
- Web Crypto API（SubtleCrypto.encrypt）替代 cryptography.io
- API key 直接存 renderer（X-API-Key header 由 renderer 添加）
- 失去 keychain 隔离 — API key 现在 100% 在用户文件系统

**风险**：
- 用户文件系统被读 → API key leak
- 当前 backend SecretStr + zeroize 防护失去意义（API key 不再过 Python heap）
- 需要 Phase 2+ 重新设计前端 SecretStr + sealed box pattern

## §5 风险

### 5.1 IF fork 冲突检测

当前 backend 用 DB partial unique index：

```sql
CREATE UNIQUE INDEX idx_one_active_provider
    ON ai_providers (user_id)
    WHERE is_active = 1;
```

**前端 IndexedDB 等价**：需要 `IDBTransaction` 内手动检查 + abort。容易出错。

### 5.2 Snapshot 协调

v0.5 backend `fingerprint` (SHA256) 是 content-addressed。Multi-device sync 通过 server-side dedup 实现。

**前端方案**：每个设备独立 IndexedDB；无 dedup；同内容可能在两设备存两份。

### 5.3 安全：API key 100% 用户端

当前 backend SecretStr 保证：
- API key 仅在 HTTP 请求栈帧存在
- `__repr__` 返回 `***`
- `__del__` 清零 bytearray

**前端 renderer**：
- API key 必须在 localStorage / IndexedDB 至少存一次（用于下次启动）
- 任何 XSS / supply-chain 攻击都可能泄露
- 需要 Electron `contextIsolation: true` + CSP 严格

### 5.4 失去 server-side audit

当前 backend `audit_events` 表记录"who did what when"。**前端 IndexedDB 也可记录**，但用户可清空 localStorage → audit 失效。

### 5.5 WebSocket 状态共享

chat_ws.py 提供 multi-tab chat broadcast。**前端 BroadcastChannel API** 仅 single-origin / single-browser；多设备 chat 完全消失。

### 5.6 Python 生态依赖

- 当前 backend 用 SQLAlchemy 2.0 + alembic + cryptography + anthropic SDK
- 这些是 Python 生态最成熟的库
- 前端 IndexedDB 没有等价成熟方案（Dexie.js 4 是 best，但 version migration 仍需手动写）

## §6 决策建议：**保留 backend**（理由）

### 6.1 主要论点

1. **v0.5 已稳定**：13 commits + 532 passing tests + 39 endpoints + ProviderResolver + SecretStr 安全机制。
2. **用户价值集中在 UI + IF/Snapshot**：frontend 工程是主要工作量；backend 是基础设施支持层。
3. **中国网文 BYOK 信任模型**：用户自带 API key 直连 Anthropic/MiniMax proxy。server-side 隔离提供额外保护（API key 不直接暴露在 renderer DevTools Network tab）。
4. **Phase 2 已规划 Electron 主进程 + Sentry + OTel**：这些依赖 backend 的 structured logging。
5. **A11y 4 门禁 + IF UI 接通**：不依赖 backend 选择。
6. **风险/收益比不划算**：6-12 个月重写 vs 增量改进 v0.5 → v0.6。

### 6.2 Option C 适用条件（暂不满足）

Option C 可行**仅当**：

- v0.5 维护成本 > 重写成本（目前不是 — 532 tests pass, 0 P0 bugs）
- 团队规模 >= 5 FTE（目前 3 workers）
- Multi-device sync 不需要（v0.5 已是 single-device Electron app — 但 backend 提供 future 扩展性）
- 用户强烈反对 Python 子进程（无 evidence）

### 6.3 折中：Option E（保留 backend 但最小化）

作为 **P3-Removal** 后续选项，保留 Option C 的代码路径：

- 当前 Phase 1 完成的 41 endpoints 保留
- 新功能（Phase 2+）优先在 frontend IndexedDB 实现（offline-first）
- 仅当涉及 multi-device / multi-user 时落到 backend
- 任何 backend 改动必须 ≥ 50% test coverage

### 6.4 触发 Option C 重评估的条件（监控指标）

未来 6-12 个月观察：

1. **Backend maintenance cost** > 30% dev time → 触发
2. **Multi-device sync demand** = 0 → 仍可保留
3. **Multi-device sync demand** > 50% users → 强烈触发 Option C
4. **Python 生态问题**（如 SSL DLL）影响 > 5% users → 触发
5. **Team size** 增长到 5+ → 重新评估人力配置

    """Bytes-backed secret wrapper; minimizes plaintext lifetime."""
    __slots__ = ("_buf",)

    def __init__(self, plaintext: str):
        if not isinstance(plaintext, str):
            raise TypeError(...)
        self._buf = bytearray(plaintext.encode("utf-8"))

    def __repr__(self) -> str:
        return "***"

    def __str__(self) -> str:
        raise SecretAccessError(...)

    def __format__(self, format_spec: str) -> str:
        raise SecretAccessError(...)

    def get(self) -> str:
        return self._buf.decode("utf-8")

    def clear(self) -> None:
        for i in range(len(self._buf)):
            self._buf[i] = 0
        self._buf.clear()

    def __del__(self):
        try:
            self.clear()

        raise TypeError("SecretStr instances cannot be pickled.")
